# LLVM ORC JIT fixed HashWX

`main.cpp` parses and validates the complete 32×8 canonical `program.json`, emits the full 13-opcode / two-scratch-phase HashWX algorithm and SipHash stages as LLVM IR, runs the explicitly selected LLVM O0/O1/O2/O3 IR pass pipeline, and generates real native code at runtime through ORC LLJIT with aggressive codegen. The measured XOR-accumulating `bench(start,count)` loop is generated inside JIT code and calls the generated `hash(salt)` function, exactly as in the Wasmtime/Cranelift batch setups.

Interfaces: normal benchmark output (`ENGINE`, `MODE jit-batch`, `BUILD_US`, `FIRST_US`, `CHECK`, seven configurable `RATE sink=` lines), `--version`, `--hash-salts SALTS.hex` and `--batch-cases CASES.hex`. The latter independently folds each range in the host over the *JIT-compiled hash* before emitting the JIT-batch sink. `CODE` is intentionally not reported because a trustworthy machine-code byte size has not been instrumented. The runner verifies `MODE jit-batch` in `tools/bench.py`.

Development build: `tools/build-llvm-orc.sh /home/jan/build/museum-of-jit/llvm-orc-20261104/llvm-orc-hashwx` on Acer with existing managed sccache C++ wrapper; do not start another daemon or bypass sccache. The harness runner accepts `MUSEUM_LLVM_ORC_BIN=/path/to/pinned/executable` and an optional `MUSEUM_LLVM_ORC_LIBDIR=/path/to/pinned/dependencies`. Keep runtime/build artifacts outside this source directory.

Correctness was established on Acer against the independent fixed Wasm emitter with the existing reproducible two validators (100,000 individual salts, 627 batch ranges including zero and wraparound). The full 300,000-hash sink matched `1842ddbd4c0fefed`. The production LLVM21.1.8 executable passed exact oracles on both Acer and cold-storage EPYC9655 CPU0, and a fully validated CPU0 30k/7×300k benchmark has been accepted into `results/epyc-9655-zen5-llvm-orc-2026-11-04.json`, with the five additional complete controls under `results/diagnostics/`. The initial LLVM23.1.4 Acer-only prototype could not run on Debian13 cold-storage because its dynamic LLVM library requires glibc2.44; it is not a canonical benchmark.

## Target-compatible runtime

The production benchmark uses the existing self-contained **LLVM 21.1.8** toolchain built for older glibc, not the system LLVM 23 library from Acer's newer userspace. Set `MUSEUM_LLVM_CONFIG=/home/jan/build/museum-jit-cpython-3.15.2-jit-toolchain/LLVM-21.1.8-Linux-X64/bin/llvm-config` when building on Acer. LLVM's ORC engine and optimizer are linked statically from this toolchain; the resulting executable has been verified on Debian 13 cold-storage without a second LLVM runtime or libc installed. The initial LLVM23 prototype passed all oracles on Acer but was not deployable on cold-storage because its dynamic libLLVM needed glibc2.44.

For cross-distro linking on Acer, also set `MUSEUM_LLVM_TARGET_LIBM_DIR=/home/jan/build/museum-of-jit/llvm-orc-20261104/target-glibc241`, containing an unchanged copy of Debian13 cold-storage `libm.so.6` and `libm.so -> libm.so.6`. This is used only at **link time** to resolve versioned `sinh`/`cosh` symbols against glibc2.41-compatible exports (GLIBC_2.2.5), not to run an older math library in the JIT process. Without it, Acer's newer host library binds `sinh`/`cosh` to GLIBC_2.44, making an otherwise static-LLVM binary unloadable on Debian13. The dynamic dependencies and symbol versions must be checked on the actual final executable; a static LLVM link alone is not sufficient. The exact target `libm.so.6` SHA256 on 2026-11-04 is `6d567d53e895273ca14a1f9dc164fc6c8d39aed2f60aa46a733c2784228915f3`.

## Controlled IR optimization policy experiments

In addition to the accepted **O2** default (`llvm-orc`), the same pinned LLVM21 ORC LLJIT binary accepts `MUSEUM_LLVM_IR_OPT=O0|O1|O2|O3`. An unset variable is **O2**; all other strings are errors, never silently mapped to a different policy. The O0 case uses LLVM PassBuilder's dedicated `buildO0DefaultPipeline`, while O1/O2/O3 use `buildPerModuleDefaultPipeline`. All policies still use the **same** fully validated HashWX LLVM IR emitter and `CodeGenOptLevel::Aggressive` for native code emission, as well as the same native in-JIT `bench` function with `noinline` `hash` call. No interpreter or AOT implementation is involved.

The independent harness adapters `llvm-orc-o0`, `llvm-orc-o1`, `llvm-orc` (O2) and `llvm-orc-o3` each select their exact policy and **require a matching `IR_OPT O*` attestation** from the executable. The recorded runtime version includes the selected level, and wrong/missing/repeated policy attestations invalidate a run. Use `MUSEUM_LLVM_ORC_BIN` to select a precisely checksummed, target-compatible host binary from a versioned build/runtime directory; the original accepted O2 executable and dataset are unchanged. For strict apples-to-apples measurements, explicitly pin CPU affinity to CPU0 and use `MUSEUM_WARMUP=30000`, `MUSEUM_ITERATIONS=300000`, `MUSEUM_SAMPLES=7` with the existing harness. Each variant must pass the independent 100,000-salt oracle and 627 batch-range tests before a canonical throughput result is accepted. An O0 variant that cannot complete this protocol in the allotted run budget should be reported as such rather than included with mismatched dimensions.

### Verified policy result (EPYC 9655, 2026-11-05)

For this **specific fixed HashWX workload**, the recommended LLVM IR policy is **O0**, chosen with adapter `llvm-orc-o0` (or by passing `MUSEUM_LLVM_IR_OPT=O0` to the executable). This does not mean unoptimized machine code: `CodeGenOptLevel::Aggressive` remains enabled. All four policies are independently correct for 100,000 salts and 627 three-way batch cases on both Acer and EPYC9655 CPU0. Four complete CPU0 O0 runs averaged **326,104 hashes/s**, versus four matched O2 runs at **291,695 hashes/s** (**+11.8%**). O0 also took **45.2 ms** to compile versus O2's **421.2 ms** (**9.3× faster build**). Cranelift native batch control was **349,908 H/s** with ~9.5 ms compilation; Wasmtime batch was **348,378 H/s**. All benchmark runs use the canonical 30k warmup and 7×300k measured dimensions with correct sinks, and full primary/diagnostic datasets, source/ABI details, raw SHA manifest and limitations are tracked in `results/README.md` and `results/diagnostics/README.md`.

The **default `llvm-orc` adapter intentionally continues to attest O2** for interpretability of the original accepted 2026-11-04 data; use the explicit **`llvm-orc-o0`** adapter for best measured LLVM behavior. No implicit benchmark identity switch or silent baseline rewrite. The underlying executable remains configurable across all four policies and defaults to O2 when run without a selector. A separate machine-code investigation would be needed to explain *why* this workload benefits from the O0 IR path; the results do not prove a general defect in LLVM optimization.

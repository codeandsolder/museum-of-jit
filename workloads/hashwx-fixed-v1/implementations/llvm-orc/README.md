# LLVM ORC JIT fixed HashWX

`main.cpp` parses and validates the complete 32×8 canonical `program.json`, emits the full 13-opcode / two-scratch-phase HashWX algorithm and SipHash stages as LLVM IR, runs the LLVM O2 IR optimization pipeline, and generates real native code at runtime through ORC LLJIT with aggressive codegen. The measured XOR-accumulating `bench(start,count)` loop is generated inside JIT code and calls the generated `hash(salt)` function, exactly as in the Wasmtime/Cranelift batch setups.

Interfaces: normal benchmark output (`ENGINE`, `MODE jit-batch`, `BUILD_US`, `FIRST_US`, `CHECK`, seven configurable `RATE sink=` lines), `--version`, `--hash-salts SALTS.hex` and `--batch-cases CASES.hex`. The latter independently folds each range in the host over the *JIT-compiled hash* before emitting the JIT-batch sink. `CODE` is intentionally not reported because a trustworthy machine-code byte size has not been instrumented. The runner verifies `MODE jit-batch` in `tools/bench.py`.

Development build: `tools/build-llvm-orc.sh /home/jan/build/museum-of-jit/llvm-orc-20261104/llvm-orc-hashwx` on Acer with existing managed sccache C++ wrapper; do not start another daemon or bypass sccache. The harness runner accepts `MUSEUM_LLVM_ORC_BIN=/path/to/pinned/executable` and an optional `MUSEUM_LLVM_ORC_LIBDIR=/path/to/pinned/dependencies`. Keep runtime/build artifacts outside this source directory.

Correctness was established on Acer against the independent fixed Wasm emitter with the existing reproducible two validators (100,000 individual salts, 627 batch ranges including zero and wraparound). The full 300,000-hash sink matched `1842ddbd4c0fefed`. The production LLVM21.1.8 executable passed exact oracles on both Acer and cold-storage EPYC9655 CPU0, and a fully validated CPU0 30k/7×300k benchmark has been accepted into `results/epyc-9655-zen5-llvm-orc-2026-11-04.json`, with the five additional complete controls under `results/diagnostics/`. The initial LLVM23.1.4 Acer-only prototype could not run on Debian13 cold-storage because its dynamic LLVM library requires glibc2.44; it is not a canonical benchmark.

## Target-compatible runtime

The production benchmark uses the existing self-contained **LLVM 21.1.8** toolchain built for older glibc, not the system LLVM 23 library from Acer's newer userspace. Set `MUSEUM_LLVM_CONFIG=/home/jan/build/museum-jit-cpython-3.15.2-jit-toolchain/LLVM-21.1.8-Linux-X64/bin/llvm-config` when building on Acer. LLVM's ORC engine and optimizer are linked statically from this toolchain; the resulting executable has been verified on Debian 13 cold-storage without a second LLVM runtime or libc installed. The initial LLVM23 prototype passed all oracles on Acer but was not deployable on cold-storage because its dynamic libLLVM needed glibc2.44.

For cross-distro linking on Acer, also set `MUSEUM_LLVM_TARGET_LIBM_DIR=/home/jan/build/museum-of-jit/llvm-orc-20261104/target-glibc241`, containing an unchanged copy of Debian13 cold-storage `libm.so.6` and `libm.so -> libm.so.6`. This is used only at **link time** to resolve versioned `sinh`/`cosh` symbols against glibc2.41-compatible exports (GLIBC_2.2.5), not to run an older math library in the JIT process. Without it, Acer's newer host library binds `sinh`/`cosh` to GLIBC_2.44, making an otherwise static-LLVM binary unloadable on Debian13. The dynamic dependencies and symbol versions must be checked on the actual final executable; a static LLVM link alone is not sufficient. The exact target `libm.so.6` SHA256 on 2026-11-04 is `6d567d53e895273ca14a1f9dc164fc6c8d39aed2f60aa46a733c2784228915f3`.
